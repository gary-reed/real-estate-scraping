# template-real-estate-scraper

Starting point for an AI-generated scraper of a **property-listing website**: the `cms` flavor of [multi-scraper-framework](https://github.com/andre-mei/multi-scraper-framework) plus
the `real-estate` dialect (`dialect-real-estate` in this project). The Manager connection, commands and the
UI come from the framework: a scraper needs nothing new for them.

This template, the dialect, and the model were generated by an AI agent from that framework's [docs/prompts/example-prompt-scraping.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/prompts/example-prompt-scraping.md) for real estate. The way to turn this template into a scraper for a specific property portal is the AI prompt [docs/ai-scraper-recon-prompt.md](../../docs/ai-scraper-recon-prompt.md). Start there and give it to an AI agent. The repository [README](../../README.md) has the clone and install steps. This file is the reference for each file in the template, which that AI prompt tells the AI agent to follow.

The framework guide for the Manager, proxies, and `scraper.mode` is [docs/GUIDE.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/GUIDE.md).

It contains **no site-specific logic**. It compiles, and every site-dependent method is either a
compile-safe default or throws `UnsupportedOperationException("... not implemented")`, with a
detailed Javadoc/comment block explaining **what the method must return, how to find it on the
target site, and which pitfalls to check**.

Two audiences:

1. **A developer cloning it** for a new site (checklist below).
2. **An AI agent** that analyses a target property site and builds the complete scraper from this template
   (implementation + `RECON.md` blueprint): the comments in each method are the specification of what
   to find and implement. Every method comment maps to a section of the AI prompt
   (see `docs/ai-scraper-recon-prompt.md`). Where a comment and the model classes
   disagree, the model wins.

> The template cannot run a scrape by design: Phase 0 (`sampleSearch`,
> `validateListingId`, `validateListingDetailsParsing`) and Phase 1/2 methods throw until implemented.

## Layout

| File | What it is | Site-specific content to provide |
|---|---|---|
| `TemplateScraperApplication` | entry point (`@SpringBootApplication @EnableCmsFlavor`) | rename package/class |
| `TemplateConstants` | Site constants and **split filter definitions** (`OPERATIONS`, `REGIONS`, `PRICES_RENT/BUY`, `SURFACES`, `PROPERTY_TYPES`, page size, max per search) | all values (data only, no logic) |
| `phase/TemplateScraperDetails` | `ScraperBasicDetails`: alias, base domain, page size, max per search, language, country, currency | all getters |
| `phase/TemplatePhase0` | Validation: fixture search URL, id format, assertions on the parsed listing | fixture + assertions |
| `phase/TemplatePhase1` | Splitting: basic splits (generic), `parseSplitCount`, `getFilterPriority`, `buildUrlFromFilters`, `shouldSkipSplit` | count parser, URL grammar, filter order |
| `phase/TemplatePhase2` | Crawling: `resolvePagination`, `resolveListingIDs`, `resolveIdFromListingUrl`, crawl enrichment, `getPhaseBaseUrl` | pagination, card selectors, id regex |
| `phase/TemplatePhase3` | Detail parsing: `parseListingDetails` split in per-block methods, AJAX captures, `wasDelisted`, language | the whole detail page mapping |
| `phase/TemplateMediaParser` | Gallery / floorplan / video / virtual tour | gallery source + URL rules |
| `TemplateBrowserBehavior` | Pop-ups, cookie banner, and block-page text for `scraper.mode: BROWSER` | selectors |
| `TemplateSiteBrowserProfile` | The same behavior **as data** for `scraper.mode: DELEGATED`, plus `hostMatch` and delisted rules | selectors + delisted rules |
| `application.yaml` | Scraper/browser config; lines marked `TEMPLATE:` need review | name, port, DB path, country, delays |
| `logback-spring.xml` | Logging (unchanged except default app name) | none |

## Cloning checklist (new site `<site>-<cc>`)

1. Copy the folder to `scrapers/<site>-<cc>-scraper`; add it to the `<modules>` list in the root `pom.xml`.
2. Rename: artifactId / `<name>` / description in `pom.xml`; package `com.realestate.template` → `com.realestate.<site>`;
   classes `Template*` → `<Site>*`; the main class;
   `application.yaml` (`spring.application.name`, `scraper.name` = site alias, `server.port`, the SQLite path
   under `./data/`, `target-country`, `currency`); logback default app name. Working files stay inside this module.
3. Fill in, in this order (each step is testable on its own, and later steps need the earlier ones):
   1. `TemplateScraperDetails`.
   2. `TemplateConstants`: operations, **one small location only while developing**, price/surface/type lists.
   3. `TemplatePhase1.buildUrlFromFilters` and `parseSplitCount`. Check by hand: every filter changes the count; the
      count equals the number of unique ids over all pages of two small searches.
   4. `TemplatePhase2` (`resolveIdFromListingUrl`, `resolvePagination`, `resolveListingIDs`).
   5. `TemplatePhase3` + `TemplateMediaParser` (+ AJAX captures for lazy data such as coordinates and the
      contact phone/email, `wasDelisted`, the mandatory-fields gate). Parse saved HTML fixtures in unit tests first.
   6. `TemplatePhase0` fixture and assertions (needs a working Phase 2 + Phase 3). The fixture search must return
      more than one full page: Phase 0 requires exactly `expectedListingsPerPage` ids on its page 1.
   7. `scraper.mode` (see the decision notes in `application.yaml`). **HTTP: delete `TemplateBrowserBehavior` and
      `TemplateSiteBrowserProfile`** (and their tests). **DELEGATED / BROWSER: fill
      both**, keep them in sync, and add a test that pins them together.
   8. `getFilterPriority` order from measured drill-down trees (see its Javadoc), then enlarge the active location list.
4. Tests worth adding: `wasDelisted` with saved HTML (live / removed / block page), media parser on a
   saved page, count parser on saved search pages (including zero-results and block pages), `resolveListingIDs` returning
   exactly the organic listings (= `expectedListingsPerPage` on a full page), contact extraction (private and agency),
   the reject rule (a listing without contact / with an unmapped value parses to `null`), USD conversion for non-USD
   sites, and (browser modes only) browser profile ↔ behavior sync.
5. First live run: few workers (1-3), small location, check Phase 0 passes, then Phase 1 tree and Phase 2 totals.
   Live runs on real proxies are done by the developer, never automatically.

## Where each recon-blueprint item lands

| Blueprint item | Goes to |
|---|---|
| Site identity, language, currency, page cap, results per page | `TemplateScraperDetails`, `TemplateConstants` |
| Scope (operations / categories) and their URL tokens | `TemplateConstants.OPERATIONS` (+ README note for excluded categories) |
| URL grammar (search, filters, page N, detail) | `TemplatePhase1.buildUrlFromFilters`, `TemplatePhase2.resolvePagination` |
| Location hierarchy and the full list for the basic level | `TemplateConstants.REGIONS` |
| Result count (element/JSON, format, cap, zero vs block page) | `TemplatePhase1.parseSplitCount` |
| Filter inventory, open-ended/inclusive/leakage/invalid-value tests | `TemplateConstants` (value lists + comments) |
| Filter priority (drill-down trees) | `TemplatePhase1.getFilterPriority` |
| Pagination, cap, promoted/"nearby" results | `TemplatePhase2` |
| Result-page composition (organic vs featured extras, ads, projects) | `TemplatePhase2.resolveListingIDs`, `expectedListingsPerPage` |
| Result cards, id regex, tracking params, special cards, card price/image count | `TemplatePhase2.resolveListingIDs`, `resolveIdFromListingUrl`, `supportsCrawlEnrichment` |
| Detail data sources and field map | `TemplatePhase3` (per-block methods), `TemplateMediaParser` |
| Lazy content (scroll / fetch / click, XHR) | `getPhase3AjaxCaptures` |
| Delisted detection | `TemplatePhase3.wasDelisted` (+ `DelistedRules` in the profile) |
| Type/subtype mapping table (mandatory) | `TemplatePhase3.parseBasic`, `mandatoryGaps` |
| Coordinates, address, precision + `isPrecise` rule | `TemplatePhase3.parseAddress`, `parseCoordinates` |
| Advertiser type, contact phone/email (mandatory) and its mechanism, login/form-only verdict | `TemplatePhase3.parseContactInfo`, `getPhase3AjaxCaptures`, `mandatoryGaps` |
| Advertiser's own reference vs the site's listing id | `contact.extRefId` (`parseExternalReference`) vs `scrapingDetails.externalId` (`parseListingDetails`) |
| Currency (non-USD) | `getExchangeRate()` (keep), `basic.price` in site currency |
| Tags | `ScrapingTaggingEnum` slots, table in the README |
| HTTP vs browser decision | `scraper.mode` in `application.yaml` (+ keep or delete the browser classes) |
| Consent button, other pop-ups, block-page text, host match, delisted rules | `TemplateBrowserBehavior`, `TemplateSiteBrowserProfile` |
| Phase 0 fixture | `TemplatePhase0` |

## Conventions

- Log `[PARSING_SPECIFIC]` when something this site *always* has is missing (layout probably changed) and
  `[PARSING_PENDING]` when something unhandled shows up (new subtype, unexpected address shape). They are grepped to
  find what to implement next.
- `parseSplitCount` returns `-1` (never `0`) when the count cannot be read; `0` only when the page says "no results".
- Range boundary lists never contain `"0"`; split filters keep the same `shortName` across operations ("Price").
- A missing mandatory field that depends on browser capture (e.g. coordinates, phone) throws `DetailParseRetryException` so
  the listing is retried instead of stored incomplete.
- **Reject rather than store**: when something important is unresolved (operation, type, subtype, contact phone/email,
  site-specific mandatory fields, an unmapped value), log `[PARSING_PENDING]` and return `null` from `parseListingDetails`.
  The listing is not saved and comes back in the next run until the parser is fixed. Only documented exceptions are stored.
- Two different ids: `contact.extRefId` = the advertiser's own reference ("Ref: AB-1234"); `scrapingDetails.externalId` =
  the site's own listing id, raw (without the alias prefix).
- `location.isPrecise` is set by the parser with a rule relative to the site's typical precision (see `parseAddress`).
- Tags: the pipeline adds `GENERIC_*` tags; the parser adds `GENERIC_RESOLVED_*_FROM_DESC` or a `SCRAPER_FIXED_*` slot when it
  fills a value by a site-specific fix or inference, and the README lists what each slot means for the site.
- Read-only: never log in, create accounts, submit contact forms or save searches. "Show phone/email" is clicked only to
  analyse its mechanism during the recon; the scraper captures it with a quiet `fetch` when possible (`click` = fallback).
- Keep browser work in the background (no foreground window pop-ups).
- Model gaps (note in the blueprint / README if the site publishes them; do not invent fields):
  - minimum / maximum stay
  - price drop / "was X, now Y" (do **not** put that in `basic.originalPrice`)
  - listing title / featured / premium / price-qualifier (POA, guide price…) — `Display` is commercial
    street-front only; for POA leave `basic.price` null
- `basic.originalPrice` means the asking price in the **site currency** after USD conversion
  (`postProcess` fills it from `price` for non-USD sites). Scrapers normally set only `price` in
  site currency and leave `originalPrice` null.

## How the UI learns about this scraper

Nothing in this module needs to describe itself to the Manager or the UI. The flavor engine sends a **flavor
descriptor** inside `REGISTER` (built by `CmsFlavor.descriptor()` in `flavor-cms`): the stages, the data
tables, the Central DB sink and the log group titles. The Manager forwards it unchanged and the UI renders from it, so
stage badges, the Continue/Resume buttons, the Data sub-tabs and the Central DB tab need no per-site work.

The Central DB tab pushes the warehouse to the `central-db` sink consumer as dataset `listings`, using the site alias
as the source and the scraper's country as context (`CmsOutputSink`). The consumer's address and token come from
`scraper.sink-consumers.central-db` (env `CENTRAL_DB_API_URL`, `CENTRAL_DB_INTERNAL_TOKEN`); a site scraper does not
touch them. The scraper never connects to a database of yours: it calls your consumer's HTTP API, see
[docs/reference/sink-consumer-api.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/reference/sink-consumer-api.md).
This dialect can be that consumer and write a CSV. The spreadsheet name is `realestate.csv-sink.file-name`
(default `listings.csv`). See [docs/dialect.md](../../docs/dialect.md).

- Data tab URLs are built from the table **keys** (`/scrapers/<id>/data/temp_listing_ids`), so renaming a label
  changes nothing. Old label-based links still open the right sub-tab.
- Collapsible log groups follow one marker pattern, for any `KIND`:
  `[<KIND>_GROUP_START:<id>|<detail>]` ... `[<KIND>_GROUP_END:<id>]`. If `<detail>` starts with `http(s)://` it is shown
  as the group's URL, otherwise it is the title. Existing kinds: `PARSE` (listing parse) and `SPLIT`.

The full contract (descriptor, commands, events, what a flavor must guarantee) is in
[docs/reference/flavor-contract.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/reference/flavor-contract.md).
