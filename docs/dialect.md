# The real-estate dialect

This page is the property layer of an AI scraper project. To add a portal, start with the repository [README](../README.md): it shows how to give the AI prompt [docs/ai-scraper-recon-prompt.md](ai-scraper-recon-prompt.md) to an AI agent.

The engine is [multi-scraper-framework](https://github.com/andre-mei/multi-scraper-framework). This repository was generated by an AI agent from that project's [docs/prompts/example-prompt-scraping.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/prompts/example-prompt-scraping.md), filled in for real estate. It adds a property listing on top of the framework's `cms` flavor. It does not modify the framework. A site scraper is a separate module the AI prompt generates from the template. The modules in this build are:

| Module | What it is |
| --- | --- |
| `real-estate-model` | `RealEstateListing` and its blocks. Depends on `scraper-model` only. No Spring, HTTP, or browser. |
| `dialect-real-estate` | Parser base, description resolvers, anomaly checks, USD conversion, warehouse columns. |
| `templates/template-real-estate-scraper` | The starting point for a site. No site logic. |

A scraper uses parent `com.scraper:scraper-parent:2.0.0-SNAPSHOT`, `@SpringBootApplication @EnableCmsFlavor`, and the dependencies `flavor-cms` and `dialect-real-estate`. `application.yaml` sets `scraper.flavor: cms-listings` and `scraper.dialect: real-estate`. Phase 3 `extends RealEstateParser`. The dialect registers itself through its jar. The yaml key only checks that the expected dialect is on the classpath.

The Manager, the Browser Delegator, HTTP versus a browser, and the sink consumer are the framework's. Read [docs/GUIDE.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/GUIDE.md) for those.

## What a parser fills

`RealEstateListing` extends the framework's `_ListingDetails`.

| Block | What it holds |
| --- | --- |
| `Basic` | Operation (`BUY`, `RENT`, `SHARE`), term, type, subtype, price, currency |
| `Location` | Address parts, coordinates, precision. Framework type. |
| `Property` | Rooms, surface, floor, condition, amenities |
| `Building` | Year, height, plot, parking, facilities |
| `Interior` | Kitchen, bathrooms, room sizes |
| `Furnish` | Furnished state, appliances, heating |
| `Transaction` | Deposit, fees, availability, policies, tenure |
| `ContactExternal` | Advertiser, phone, email, the advertiser's own reference (`extRefId`) |
| `FlatMate` | Room-share household, when the site has one |
| `Display` | Commercial street frontage only. No title, no featured flag. |
| `RealEstateMedia` | Gallery and video, from the framework `Media`, plus a floor plan and a virtual tour |
| `ScrapingDetails` | The site's listing id (`externalId`), tags, ignore reason. Framework type. |

`AnnounceTypeEnum` is on `RealEstateListing`. Set a subtype with `setPropertySubType(SubTypeEnum…)`. `RES_LOFT` and `RES_DUPLEX` share the integer `4`, so a subtype is never stored by that integer.

`contactExternal.extRefId` is the advertiser's own reference. `scrapingDetails.externalId` is the site's listing id, without the site-alias prefix. The full id the engine stores is `<alias><rawId>`.

## What the dialect does after the parse

`ScraperParser.executeParseLogic` checks `wasDelisted`, calls `parseListingDetails`, calls `finish`, then stamps `scrapedDate`. The property steps are `RealEstateParser.postProcess`, which `finish` runs when the parse returned a listing:

1. Clean the listing.
2. Anomaly check.
3. Description resolvers, on fields that are still null. They add `GENERIC_RESOLVED_*` tags.
4. Anomaly check again, now with the description.
5. Convert `basic.price` to USD.
6. Price ratio, floor-category amenity, and the term price.

A null return from `parseListingDetails` skips all of that. The listing is not stored and comes back on the next run.

The automatic resolvers are `PropertyResolver`, `TransactionResolver`, `BuildingResolver`, `FurnishResolver`, and `InteriorResolver`. They can fill bedrooms, bathrooms, surface, floor, amenities, view, condition, deposit, availability, policies, ownership, parking, facilities, land, building height and age, furnishing, heating, appliances, and interior bath details. They do not fill operation, type, subtype, price, currency, coordinates, or contact. `PropertySubtypeTextResolver` is a helper the parser calls itself. It is not in that list.

Nothing in the pipeline geocodes an address. A missing coordinate stays missing.

## Language

`ScraperBasicDetails.getLanguage()` is a `ScraperLanguage` (browser locale and proxy preference). `RealEstateParser.getLanguage()` is a `ParserLanguage` (the text the resolvers read). Pick the description language for the second one.

Resolver dictionaries exist for English, Spanish, German, French, and Italian. Portuguese, Dutch, and Polish exist as `ScraperLanguage` only. Do not add a `ParserLanguage`. If the descriptions are another language, say so in the scraper's `RECON.md`, and choose one of the five only after checking that its keywords do not match the sample text by accident.

## Price

The warehouse stores USD in `price`. The parser sets `basic.currency` and `basic.price` to the amount printed on the site, and leaves `originalPrice` null. For a non-USD currency, `postProcess` copies that amount into `originalPrice` and stores `price * rate` in `price`. The rate is how many USD equal 1 unit of the site currency. The dialect asks [Frankfurter](https://www.frankfurter.app) for that number (`https://api.frankfurter.dev/v1/latest?from=<code>&to=USD`, no API key) through `UsdRateClient`. It does not use the rate on `ScraperConfig`: the framework treats EUR as the currency that needs no rate, and the number it stores for any other code is an EUR quote. `realestate.usd-rate.url` replaces the Frankfurter URL if that host moves.

The same client also answers `GET /api/v1/currencyRate/<code>` with `{"rate": <USD per 1 unit>}`. Keep `scraper.currency-rate-endpoint: http://127.0.0.1:${server.port}/api/v1/currencyRate`. The framework calls that path for every site currency except EUR, and it aborts the run when the call fails. A USD answer is `1.0` and does not call Frankfurter. An EUR listing is converted here, because the framework does not fetch a rate for EUR.

Deposit, community charges, agency fees, and the other term slots are not converted. They stay in the site currency. `resolveAndSetTopTermPrice` copies the USD `price` into the slot of `topTerm`. A null term on a rent or share listing becomes `LONG_TERM`.

A listing priced in a currency other than the site's cannot use the site rate. The parser rejects it.

`originalPrice` is the asking price in the site currency after that conversion. It is not a previous price and not a price drop.

## Anomaly bounds

The defaults on `AnomalyBounds` are absolute numbers (500,000,000 buy, 500,000 rent, and ratios per square metre). They are generous, and they are sized like USD. `RealEstateSettings` reads `scraper.anomaly-bounds.*`. The template returns `realEstateSettings.getAnomalyBounds()`.

A site whose currency is a different size from USD scales every money bound in the parser's `getAnomalyBounds()`, so a normal rent is not rejected as above the maximum and a price-per-square-metre check does not reset the surface. Non-money bounds (bedrooms, surface in square metres) stay as they are.

## Tags

`scrapingDetails.addTag` stores the enum name. Tests read them with `hasTag`. The resolvers and `AnomalyDetector` add `GENERIC_*` tags. When the parser itself fills a value by a site-specific fix rather than a structured field, it uses an existing `SCRAPER_FIXED_*` slot and the scraper README says what that slot means. Do not add values to `ScrapingTaggingEnum`.

There is no `SCRAPER_FIXED_OPERATION_1`, no `SCRAPER_FIXED_PRICE_1`, and no `SCRAPER_FIXED_SURFACE_1`. The slots that exist are listed in the site prompt.

## Warehouse

`RealEstateWarehouse` adds columns after the framework shell: `ann_type`, `operation`, `currency`, `property_type`, `property_subtype`, `ext_phone`. The shell insert (id, status, dates, the price column, place, url, tags, hash, coordinates, precision, `details_json`) stays in `DefaultListingWarehouse`. The price column the card is compared with is the printed amount: `originalPrice` when set, otherwise `price`.

The framework still pushes through its `central-db` sink. This version's consumer is the dialect's CSV sink (`realestate.csv-sink`): the scraper posts to it on localhost, and it writes `outputs/<country>/<site>/<yyyy-MM-dd>/<file-name>`. `<file-name>` is `realestate.csv-sink.file-name`. When the property is omitted or blank the name is `listings.csv`. The value is a file name only (no directory, no `..`); the country, site, and date folders are chosen by the sink. Turn the sink on in the scraper's `application.yaml` and set `scraper.sink.auto-push` so a completed run does that push. `scraper.sink-consumers.central-db.base-url` and `token` must match the sink. The local SQLite file stays inside the scraper module. The calls the consumer answers are the framework's [docs/reference/sink-consumer-api.md](https://github.com/andre-mei/multi-scraper-framework/blob/main/docs/reference/sink-consumer-api.md).
